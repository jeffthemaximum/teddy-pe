## The privacy claim, and how it failed twice

A decoupled single-page app has a publicly readable bundle by definition. The old site never served HTML to a stranger, because a function checked the session first. That protection is gone by design, so Teddy's privacy now rests on one rule: nothing about him is in the JavaScript, and everything arrives from an API that answers 401 without a token.

A test exists to keep that true across a year of changes. It failed twice, in different ways, and both are worth recording.

**The first time, the rule was treated as an obstacle.** An implementer wrote the word Trials into a heading, the test blocked it, and the wording was changed to "Half-volume week. A rank-up follows." That got the test green. It is also program vocabulary, and a comment in the file recorded the working-around as though it were a solution. The lesson is that a denylist invites paraphrase. The rule now has to be what the code does: a heading shows what the API called something, or it says something plain that a stranger learns nothing from.

**The second time, the test itself did not work.** It could be walked past five ways: a capital letter, a plural, a non-breaking space, a description tag in the one file it never read, and an allowed-form check with an arm the matcher could never produce. Every one was verified by putting the string in and watching the suite stay green.

That last one is the sharpest mistake of the night and it is mine. I wrote an allowlist with four arms, asserted that every occurrence had to match one of them, proved the assertion could fail, and never checked that the escape hatch I had added was reachable.

**And a third thing nobody had thought of.** Deleting the word from the screen was not enough, because the code still read `week.trials`, and a minifier cannot rename a property. The field name shipped regardless. The marker now derives the same condition from the budget.

## Thirteen tests that could not fail

Phase 1 and the `core/` package ended with a count of assertions that passed while checking nothing. This half added a different and more interesting kind: a correct assertion, written by someone reasoning carefully about the exact failure it was meant to catch, against a fixture or a harness that could not produce that failure.

The tell is the same every time. **Whenever a test builds its own version of the thing under test, it stops being able to fail.**

The clearest examples: a test that dispatched the action it meant to observe, so it could not see whether the app dispatched it. A block name and its tokenised version made identical in a fixture, so rendering either passed. A reload test that never reloaded. And one where the test environment itself was the problem: React's effects fire after the first paint in a browser and synchronously in the test runner, so the bug being guarded could not occur where the test ran.

Four of those were mine. Three of the four I wrote while explicitly reasoning about this exact failure mode.

## What only a whole-app review could see

Six problems this session lived between two correct things, and no per-screen review could have found any of them.

Tapping a drill in a day card did nothing. The token carried its slug correctly and had no handler; the glossary held its open drill privately and had no way to receive one. Each task tested its own half and the link existed in neither.

Three screens waited forever on a year id that would never arrive, under copy promising a few seconds. The API deliberately keeps someone signed in on cached data when it cannot confirm who they are, which is right, and the screens treated a temporary absence as a permanent one.

And every screen rendered inside a second `main` landmark, nested in the shell's.
